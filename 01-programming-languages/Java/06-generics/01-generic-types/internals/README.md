# 03 - Internals: How Generic Types Work in the JVM

## Scope

This topic dives into the JVM-level implementation of generic types, covering how the Java compiler transforms generic code into raw types, how type erasure works, and what bytecode is generated.

## Why It Exists

Understanding generic type internals is critical for:

- Diagnosing ClassCastException at runtime when type erasure is misunderstood
- Understanding why certain generic patterns don't work (e.g., `new T()`, `instanceof List<String>`)
- Knowing how reflection can access generic type information
- Building frameworks that work with generic types

## How the Compiler Transforms Generic Types

When you write:

```java
public class Box<T> {
    private T value;
    
    public void set(T value) { this.value = value; }
    public T get() { return value; }
}
```

The compiler transforms it to:

```java
public class Box {
    private Object value;
    
    public void set(Object value) { this.value = value; }
    public Object get() { return value; }
}
```

This process is called **type erasure**. The generic type parameter `T` is replaced with its bound (or `Object` if unbounded).

## Type Erasure Process

### Step 1: Replace Type Parameters

```
Original:                    After Erasure:
class Box<T>          →      class Box
private T value       →      private Object value
void set(T value)     →      void set(Object value)
T get()               →      Object get()
```

### Step 2: Insert Casts

When the compiler encounters code that uses generic types, it inserts appropriate casts:

```java
Box<String> box = new Box<>();
String value = box.get();    // Compiler inserts: (String) box.get();
```

### Step 3: Generate Bridge Methods

For overriding methods with covariant return types, the compiler generates bridge methods:

```java
public class StringBox extends Box<String> {
    @Override
    public String get() { return "hello"; }
}
```

The compiler generates:

```java
public class StringBox extends Box {
    @Override
    public String get() { return "hello"; }
    
    // Bridge method (generated by compiler)
    public Object get() { return this.get(); }
}
```

## What Gets Erased

| Construct | After Erasure |
|-----------|---------------|
| `T` (unbounded) | `Object` |
| `T extends Number` | `Number` |
| `T extends Comparable<T>` | `Comparable` |
| `List<String>` | `List` |
| `Map<String, Integer>` | `Map` |
| `Box<T>.set(T value)` | `Box.set(Object value)` |
| `Box<T>.get()` | `Box.get()` |

## What's Preserved

| Construct | After Erasure |
|-----------|---------------|
| `extends` bound | Kept in bytecode |
| Generic signatures | Available via reflection |
| Bridge methods | Generated for polymorphism |
| Casts | Inserted by compiler |
| `Class<T>` parameter | Runtime type information |

## JVM Bytecode Example

```java
// Original Java code
Box<String> box = new Box<>();
box.set("hello");
String s = box.get();
```

```java
// Bytecode (simplified)
aload_1           // load 'box'
ldc "hello"       // push string constant
invokevirtual Box.set(Object)V   // call set with Object parameter

aload_1           // load 'box'
invokevirtual Box.get()Ljava/lang/Object;  // call get returning Object
checkcast String  // cast to String
astore_2          // store in 's'
```

Notice:
- `Box.set(Object)V` — the method signature uses Object, not String
- `checkcast String` — the compiler inserts a cast after calling `get()`

## Reflection Access to Generic Types

Although type erasure removes generic information at runtime, the Java reflection API can access generic signatures:

```java
// Get the generic superclass
Type genericSuperclass = StringBox.class.getGenericSuperclass();
ParameterizedType pt = (ParameterizedType) genericSuperclass;
Type[] typeArguments = pt.getActualTypeArguments();
System.out.println(typeArguments[0]); // class java.lang.String
```

This works because the generic signature is stored in the class file's `Signature` attribute, not in the bytecode instructions.

## Common Pitfalls

### 1. `instanceof` with Generic Types

```java
// COMPILE ERROR: Cannot use instanceof with generic types
if (obj instanceof List<String>) { }  // Error

// WORKAROUND: Use raw type or wildcard
if (obj instanceof List<?>) { }  // OK
```

### 2. Generic Array Creation

```java
// COMPILE ERROR: Cannot create generic arrays
T[] array = new T[10];  // Error

// WORKAROUND: Use Array.newInstance() or Object[]
Object[] array = new Object[10];  // OK
```

### 3. Static Members

```java
public class Box<T> {
    // COMPILE ERROR: Cannot have static members with type parameters
    private static T value;  // Error
    
    // OK: Static members without type parameters
    private static int count;  // OK
}
```

## Performance Considerations

Type erasure happens at compile time, so there is no runtime performance cost for generics. The bytecode is identical to what you would write without generics (plus casts). The JIT compiler can optimize away the casts in many cases.

| Operation | Cost |
|-----------|------|
| Generic class instantiation | Same as raw class |
| Method call with generics | Same as raw method + possible cast |
| Cast insertion | Negligible (JIT optimizes) |
| Reflection on generic types | Moderate (signature lookup) |

## Summary

| Concept | Key Takeaway |
|---------|--------------|
| Type erasure | Compile-time process, removes generic type parameters |
| Erasure rules | `T` → `Object`, `T extends X` → `X` |
| Bridge methods | Generated for polymorphism with covariant returns |
| Cast insertion | Compiler adds casts after generic method calls |
| Reflection | Generic signatures preserved in class file metadata |
| Pitfalls | No `instanceof`, no generic arrays, no static type params |
