# Type Erasure Internals: The Complete Picture

## Scope

This is the signature topic of Generics. Type erasure is not just a compiler trick — it's a fundamental design decision that affects every line of generic code you write.

## Why Erasure Exists

Java 5 (2004) introduced generics while maintaining binary compatibility with Java 1.0-1.4 code. The JVM had to run both raw types and parameterized types. The solution: erase generic information at compile time.

### The Alternative: Reified Generics

C# chose reified generics — type information persists at runtime. Java chose erasure. Why?

| Factor | Erasure (Java) | Reified (C#) |
|--------|----------------|--------------|
| Binary compatibility | ✅ Yes | ❌ No |
| JVM modification needed | ❌ No | ✅ Yes |
| Memory overhead | Low | Higher |
| Performance | Same as raw types | Slight overhead |
| Runtime type info | ❌ No | ✅ Yes |
| Generic array creation | ❌ No | ✅ Yes |
| instanceof with generics | ❌ No | ✅ Yes |

Java chose erasure because:
1. **No JVM changes** — generics were a compiler feature only
2. **Backward compatibility** — existing code ran without recompilation
3. **Simplicity** — the JVM didn't need to understand generics

## Compiler Transformation: Step by Step

### Step 1: Type Checking

```java
// Source code
Box<String> box = new Box<>();
box.set("hello");
String s = box.get();
```

The compiler verifies:
- `Box<String>` is a valid parameterized type
- `"hello"` is assignable to `String`
- `box.get()` returns `String`

### Step 2: Erasure

```
Before erasure:                After erasure:
Box<String>              →     Box
new Box<>()              →     new Box()
box.set("hello")         →     box.set("hello")
String s = box.get()     →     String s = (String) box.get()
```

The compiler:
1. Replaces `Box<String>` with `Box`
2. Replaces `T` with `Object` (or upper bound)
3. Inserts casts where needed

### Step 3: Bridge Method Generation

For overriding methods with covariant return types:

```java
// Source
public class StringBox extends Box<String> {
    @Override
    public String get() { return "hello"; }
}
```

The compiler generates:

```java
// Bytecode
public class StringBox extends Box {
    public String get() { return "hello"; }
    
    // Bridge method — preserves polymorphism
    public Object get() { return this.get(); }
}
```

Without the bridge method, `Box.get()` returns `Object`, but `StringBox.get()` returns `String`. The bridge method ensures the override works correctly.

## Bytecode Analysis

### Using javap

```bash
# Compile
javac Box.java StringBox.java

# Disassemble
javap -c StringBox.class
```

Output:
```
public java.lang.String get();
    Code:
       0: ldc           #2  // String "hello"
       2: areturn

public java.lang.Object get();
    Code:
       0: aload_0
       1: invokevirtual #3  // Method get()Ljava/lang/String;
       4: areturn
```

The second method is the bridge method.

### What javap Reveals

| Attribute | What It Shows |
|-----------|---------------|
| `Signature` | Generic type information (for reflection) |
| `Bridge` | Bridge methods (generated by compiler) |
| `Synthetic` | Compiler-generated methods |

## Binary Compatibility

### What Erasure Preserves

1. **Method signatures** — same bytecode for `List<String>` and `List<Integer>`
2. **Field names** — generic type info stored in `Signature` attribute
3. **Class hierarchy** — subclass relationships unchanged
4. **Serialization** — raw types work with pre-generics code

### What Erasure Breaks

1. **Runtime type checks** — `instanceof List<String>` impossible
2. **Generic arrays** — `new T[]` impossible
3. **Static type parameters** — `static T value` impossible
4. **Exception type parameters** — `throws T` impossible

## Bridge Methods Deep Dive

### Scenario 1: Covariant Return Types

```java
public class Animal { }
public class Dog extends Animal { }

public class Box<T> {
    public T get() { return null; }
}

public class DogBox extends Box<Dog> {
    @Override
    public Dog get() { return new Dog(); }
}
```

Generated bytecode:
```
Dog get();           // Overriding method
Object get();        // Bridge method
```

### Scenario 2: Type Erasure in Subclasses

```java
public class Wrapper<T> {
    private T value;
    public T getValue() { return value; }
}

public class StringWrapper extends Wrapper<String> {
    @Override
    public String getValue() { return "hello"; }
}
```

Generated bytecode:
```
String getValue();   // Overriding method
Object getValue();   // Bridge method
```

### Scenario 3: Multiple Type Parameters

```java
public class Pair<A, B> {
    public A getFirst() { return null; }
    public B getSecond() { return null; }
}

public class StringIntegerPair extends Pair<String, Integer> {
    @Override
    public String getFirst() { return "hello"; }
    
    @Override
    public Integer getSecond() { return 42; }
}
```

Generated bridge methods:
```
Object getFirst();   // Bridge method
Object getSecond();  // Bridge method
```

## Why Java Chose Erasure

### Historical Context

In 2003, when Java generics were designed:
- Bill Joy (Sun Microsystems) wanted simplicity
- Java needed to run on billions of devices
- Backward compatibility was non-negotiable
- The JVM couldn't be changed without breaking everything

### Technical Reasons

1. **No JVM changes** — generics were a compiler feature
2. **Backward compatibility** — existing code ran without recompilation
3. **Simplicity** — the JVM didn't need to understand generics
4. **Performance** — no runtime overhead

### Consequences

| Consequence | Impact |
|-------------|--------|
| No `instanceof List<String>` | Use `instanceof List<?>` |
| No `new T[]` | Use `Array.newInstance()` |
| No `static T value` | Use `Class<T>` parameter |
| No generic exceptions | Use `Exception` with type tokens |
| Need TypeReference for serialization | Jackson, Gson use TypeToken |

## Summary

| Concept | Key Takeaway |
|---------|--------------|
| Erasure | Compile-time process, removes generic type parameters |
| Why | Backward compatibility with pre-Java 5 code |
| Bridge methods | Generated for polymorphism with covariant returns |
| Binary compatibility | Same bytecode for all type instantiations |
| Reified vs Erasure | Java chose erasure for simplicity and compatibility |
| Workarounds | TypeReference, Class<T>, reflection for runtime type info |
