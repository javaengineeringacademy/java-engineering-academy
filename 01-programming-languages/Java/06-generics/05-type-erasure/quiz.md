# Quiz: Type Erasure

### Q1:
What does `<T>` become after type erasure if T has no bound?

A) `T`
B) `Object`
C) The first type argument used
D) `null`

**Answer:** B — Unbounded type parameters are erased to `Object`.

---

### Q2:
True or False: You can use `instanceof List<String>` in Java.

**Answer:** False — Generic type parameters are erased at runtime, so `instanceof` cannot check them.

---

### Q3:
What is a "bridge method"?

A) A method that connects two classes in different modules
B) A compiler-generated method that preserves polymorphism after erasure
C) A deprecated method kept for compatibility
D) A method that bridges checked and unchecked exceptions

**Answer:** B — Bridge methods are generated by the compiler to ensure overriding works correctly after erasure.

---

### Q4:
What does `<T extends Comparable>` become after type erasure?

A) `Object`
B) `Comparable`
C) `T`
D) `Comparable<T>`

**Answer:** B — Bounded type parameters erase to their first (leftmost) bound.

---

### Q5:
Why is `new T[size]` illegal in Java?

A) Runtime performance issue
B) Type erasure makes `T` unknown at runtime, so array type cannot be determined
C) Arrays don't support generics
D) Both B and C

**Answer:** D — After erasure, the JVM doesn't know the component type, and Java arrays require reified type information.

---

### Q6:
Which is true about `List<String>` and `List<Integer>` at runtime?

A) They are different types
B) They are the same type (`List`) due to erasure
C) `List<String>` is a subtype of `List<Integer>`
D) They cannot exist at runtime

**Answer:** B — Type erasure removes generic type parameters, so both become raw `List`.

---

### Q7:
If you have two overloaded methods:
```java
void process(List<String> list) { }
void process(List<Integer> list) { }
```
What happens?

A) They coexist fine
B) Compile error — erasure makes both `process(List)`
C) Runtime dispatch selects the correct one
D) Only one compiles

**Answer:** B — After erasure, both have the same signature `process(List)`, causing an overload conflict.

---

### Q8:
True or False: Type erasure is a compile-time process only.

**Answer:** True — The compiler performs erasure; the JVM operates on erased types. However, generic info is retained in class file metadata for reflection.

---

### Q9:
How can you preserve generic type information at runtime?

A) Using `Class<T>` tokens
B) Using `ParameterizedTypeReference` (Spring)
C) Using `TypeToken` (Gson)
D) All of the above

**Answer:** D — All these patterns capture generic type info before erasure occurs.

---

### Q10:
What is erased from `<T extends Comparable<T> & Serializable>`?

A) Both bounds are erased to `Object`
B) Erased to `Comparable & Serializable` (intersection type)
C) Erased to `Comparable` (first bound only)
D) Nothing — bounds are preserved at runtime

**Answer:** B — Multiple bounds erase to an intersection type; the JVM sees `Comparable & Serializable`.

---

### Q11:
True or False: You can create an instance of a generic type with `new T()`.

**Answer:** False — `T` is erased to `Object` at runtime, so `new T()` is not valid. You must pass a `Class<T>` token.

---

### Q12:
What happens when a `ClassCastException` is thrown inside generic code?

A) It's caused by type erasure failing
B) It's caused by the compiler inserting a cast that fails at runtime
C) It cannot happen in generic code
D) It's a JVM bug

**Answer:** B — The compiler inserts casts based on the generic type, and those casts can fail at runtime.

---

### Q13:
Which is NOT a limitation of type erasure?

A) Cannot use `instanceof` with generic types
B) Cannot create generic arrays
C) Cannot use primitives as type arguments
D) Cannot have multiple type parameters

**Answer:** D — Multiple type parameters are fully supported. A, B, and C are actual limitations.
