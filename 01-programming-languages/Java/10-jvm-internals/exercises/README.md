# JVM Internals Exercises

Practice JVM internals through hands-on exercises.

## Exercise 1: Analyze GC Logs

**Problem Statement:**
Run a Java application with GC logging enabled (`-Xlog:gc*`). Analyze the GC log output to determine which garbage collector is being used, identify major vs minor GC pauses, calculate the total time spent in GC, and determine if the application is experiencing excessive garbage collection.

**Expected Behavior:**
- The application runs with `-Xlog:gc*:file=gc.log:time,uptime,level,tags`.
- GC log entries include timestamps, pause times, and memory before/after.
- Major GC pauses are identified by longer pause times and larger memory reclaim.
- Total GC time is calculated as a percentage of application runtime.
- A summary report shows min/max/average pause times and GC frequency.

**Hints:**
- Use `-verbose:gc` or `-Xlog:gc*` to enable GC logging.
- Parse log entries looking for pause time patterns like `[pause 12.3ms]`.
- Use `jstat -gcutil <pid> 1000` for real-time GC monitoring.
- Compare heap usage before and after each GC event.

## Exercise 2: Find Memory Leak

**Problem Statement:**
Create a deliberate memory leak using a static `HashMap` that accumulates objects. Use `jmap` to take a heap dump, then analyze it to identify the leaking objects and their retention path.

**Expected Behavior:**
- The application leaks memory by adding objects to a static Map without removal.
- `jmap -dump:live,format=b,file=heap.hprof <pid>` captures the heap state.
- The heap dump shows the static Map growing over time.
- The retention path from GC root to the leaking objects is identified.
- After fixing the leak, the application stabilizes with constant memory usage.

**Hints:**
- Use `Runtime.getRuntime().totalMemory()` and `freeMemory()` to monitor memory.
- Take heap dumps at different times and compare object counts.
- Use Eclipse MAT or VisualVM to analyze the heap dump file.
- Look for "Dominator Tree" to find objects consuming the most memory.

## Exercise 3: Tune JVM Flags

**Problem Statement:**
Write a memory-intensive application and experiment with different JVM flags: `-Xms`, `-Xmx`, `-XX:+UseG1GC`, `-XX:MaxGCPauseMillis`, `-XX:NewRatio`, and `-XX:MetaspaceSize`. Observe the effect of each flag on performance and memory usage.

**Expected Behavior:**
- Setting `-Xms` equal to `-Xmx` avoids heap resizing pauses.
- G1GC with `-XX:MaxGCPauseMillis=50` targets 50ms max pause time.
- `-XX:NewRatio=2` sets old gen to 2x the young gen size.
- Increasing `-XX:MetaspaceSize` avoids early metaspace GC.
- Each flag change produces measurable differences in GC logs and throughput.

**Hints:**
- Use `jinfo -flags <pid>` to see current JVM flags at runtime.
- Run the application multiple times with different flag combinations.
- Measure throughput as operations/second for each configuration.
- Use `-XX:+PrintFlagsFinal` to see all effective flag values.

## Exercise 4: Read Bytecode

**Problem Statement:**
Write a simple Java class with various constructs (loops, try-catch, polymorphism, lambda expressions). Use `javap -c -v` to disassemble the bytecode. Analyze the generated bytecode to understand how each Java construct is implemented at the bytecode level.

**Expected Behavior:**
- A for loop is implemented using `goto` and comparison instructions.
- Try-catch blocks use exception table entries visible in bytecode.
- Polymorphic calls use `invokevirtual`, `invokeinterface`, or `invokestatic`.
- Lambda expressions are implemented as private methods (invokedynamic).
- String concatenation uses `StringConcatFactory` or `StringBuilder`.

**Hints:**
- Compile with `javac -g` to include debug information.
- Use `javap -c` for bytecode instructions and `-v` for verbose constant pool.
- Look at the `ExceptionTable` section for try-catch handling.
- Compare bytecode for `String +` vs `StringBuilder.append()` concatenation.

## Exercise 5: Analyze Thread Dump

**Problem Statement:**
Create an application with multiple threads in different states (running, waiting, blocked, timed waiting). Generate a thread dump using `jstack` or `kill -3` (on Unix). Analyze the dump to identify each thread's state, what it is waiting for, and whether any deadlock exists.

**Expected Behavior:**
- Thread dump shows threads in RUNNABLE, WAITING, TIMED_WAITING, and BLOCKED states.
- WAITING threads show the lock or condition they are waiting on.
- BLOCKED threads show which thread holds the lock they need.
- Deadlocked threads are clearly identified in the thread dump.
- Stack traces show the exact code location of each thread.

**Hints:**
- Use `jstack <pid>` to generate the thread dump.
- Look for "Found one Java-level deadlock" section in the output.
- Threads in WAITING state show `Object.wait()` or `LockSupport.park()`.
- Use `jthread` or VisualVM for a more readable thread dump view.

## Exercise 6: Profile Performance

**Problem Statement:**
Use `async-profiler` or `jcmd` to profile a CPU-intensive application. Generate a flame graph showing where the application spends most of its time. Identify the top 3 hottest methods and suggest optimization strategies.

**Expected Behavior:**
- The profiler captures CPU samples for a specified duration.
- A flame graph is generated showing call stack visualization.
- The widest frames represent the most time-consuming methods.
- Top hot methods are listed with their percentage of total CPU time.
- Optimization suggestions are provided for each hot method (e.g., caching, algorithm change).

**Hints:**
- Use `./profiler.sh -d 30 -f profile.html <pid>` for async-profiler.
- Use `jcmd <pid> JFR.start duration=30s filename=profile.jfr` for JDK Flight Recorder.
- Open the flame graph in a browser and hover over frames for details.
- Look for methods with self-time (not just cumulative time) as true hotspots.
