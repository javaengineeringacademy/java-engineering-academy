# Python Internals Quiz

## Question 1 (MCQ)
What is CPython?

- A) A Python implementation written in C that compiles Python to machine code
- B) The reference implementation of Python written in C that interprets bytecode
- C) A Python compiler that converts Python to C code
- D) A C library for embedding Python

**Answer: B**
**Explanation:** CPython is the reference (default) implementation of Python, written in C. It compiles Python source code to bytecode, which is then interpreted by the CPython virtual machine. Other implementations include PyPy (JIT-compiled), Jython (runs on JVM), and Cython (C-extension compiler).

## Question 2 (MCQ)
What is Python bytecode?

- A) The raw machine code executed by the CPU
- B) An intermediate representation of Python code executed by the Python virtual machine
- C) Compiled C extensions for Python
- D) Encrypted Python source code

**Answer: B**
**Explanation:** Bytecode is a low-level, platform-independent set of instructions generated by compiling Python source. Each instruction is one byte (hence the name). The `.pyc` files in `__pycache__` contain bytecode. The Python VM interprets these instructions, which is why Python is called an "interpreted" language.

## Question 3 (Code Output)
What does this code print about Python internals?

```python
import dis

def add(a, b):
    return a + b

dis.dis(add)

```

- A) The C source code of the function
- B) The bytecode instructions (LOAD_FAST, BINARY_ADD, RETURN_VALUE)
- C) The memory address of the function
- D) The compiled machine code

**Answer: B**
**Explanation:** `dis.dis()` disassembles the bytecode of a function, showing the opcodes. For `add(a, b)`, it shows: `LOAD_FAST a`, `LOAD_FAST b`, `BINARY_ADD`, `RETURN_VALUE`. This reveals the step-by-step operations the Python VM executes.

## Question 4 (MCQ)
How does CPython's reference counting work?

- A) It uses mark-and-sweep only
- B) Each object has a counter tracking how many references point to it; when it reaches 0, the object is immediately deallocated
- C) Objects are freed at program exit only
- D) It uses reference counting combined with a cyclic garbage collector

**Answer: D**
**Explanation:** CPython primarily uses reference counting (increment on assignment, decrement on deletion). When the count reaches 0, the object is freed immediately. However, reference counting alone can't handle reference cycles (A→B→A), so CPython also runs a generational garbage collector to clean up cyclic references.

## Question 5 (MCQ)
In CPython, what does the GIL protect?

- A) File system access
- B) Reference counting and built-in data structures from concurrent modification by multiple threads
- C) Network I/O operations
- D) Database connections

**Answer: B**
**Explanation:** The GIL ensures thread safety for CPython's internal state, primarily reference counting on objects and access to built-in data structures like dicts and lists. Without the GIL, reference counts could become corrupted in multi-threaded programs. This is why CPU-bound Python threads don't achieve true parallelism.

## Question 6 (Code Output)
What does this code reveal about CPython's memory management?

```python
import sys

a = [1, 2, 3]
print(sys.getrefcount(a))

b = a
print(sys.getrefcount(a))

```

- A) 1, 2
- B) 2, 3
- C) 2, 2
- D) Error: getrefcount doesn't exist

**Answer: B**
**Explanation:** `sys.getrefcount()` returns the reference count of an object. The count includes: the variable `a`, the argument passed to `getrefcount()` (which creates a temporary reference), so it shows 2 initially. After `b = a`, there are 3 references (a, b, and the temporary in getrefcount), showing 3.

## Question 7 (Bug Finding)
A developer wrote this code to understand Python's memory model. Find the issue:

```python
import gc

class Node:
    def __init__(self, value):
        self.value = value
        self.ref = None

a = Node(1)
b = Node(2)
a.ref = b
b.ref = a

del a
del b
gc.collect()

print("Objects cleaned up")

```

- A) The code has a syntax error
- B) Without gc.collect(), the cyclic reference would never be freed by reference counting alone
- C) The `del` statements don't actually remove the objects
- D) `gc.collect()` is unnecessary and causes errors

**Answer: B**
**Explanation:** The code creates a reference cycle (a→b→a). Reference counting alone can't free these objects because each still has a non-zero reference count from the other. The cyclic garbage collector (`gc.collect()`) detects and frees such cycles. Without explicit collection, they're freed during periodic automatic GC cycles.

## Question 8 (MCQ)
What is the purpose of `__slots__` in CPython?

- A) To define class constants
- B) To restrict attributes to a fixed set and reduce memory usage by eliminating the instance `__dict__`
- C) To define slot machine game mechanics
- D) To reserve memory for future attributes

**Answer: B**
**Explanation:** `__slots__` tells Python to allocate space for only the listed attributes, not a full `__dict__` per instance. This saves ~40-60 bytes per instance and provides faster attribute access. It also prevents accidentally adding new attributes. Classes with `__slots__` can't have arbitrary attributes added at runtime.

## Question 9 (Scenario)
You're debugging a memory leak in a long-running Python application. Which CPython tools and techniques would you use?

- A) Only use `print()` statements
- B) Use `gc.get_objects()`, `objgraph`, `tracemalloc`, and weak references to track object retention
- C) Restart the application periodically
- D) Increase system RAM

**Answer: B**
**Explanation:** CPython provides several memory debugging tools: `gc.get_objects()` lists all tracked objects, `objgraph` visualizes object references, `tracemalloc` tracks memory allocations by source, and `weakref` allows observing objects without preventing garbage collection. The `gc` module can also show which objects prevent garbage collection via `gc.garbage`.

## Question 10 (Architecture)
When designing a performance-critical Python application, how does understanding CPython internals help?

- A) It doesn't matter; Python is always slow
- B) Knowing that CPython is reference-counted, single-threaded (GIL), and uses bytecode helps you write code that minimizes object creation, avoids GIL contention, and leverages C extensions
- C) Only matters for writing C extensions
- D) Only important for PyPy optimization

**Answer: B**
**Explanation:** Understanding CPython internals lets you: (1) minimize temporary object creation (reference counting overhead), (2) use multiprocessing over threading for CPU-bound work (GIL), (3) use built-in C-implemented functions which bypass bytecode overhead, (4) understand that `__slots__` and `__pypy__` annotations can optimize memory. This knowledge directly impacts architectural decisions.
